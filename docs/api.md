# API

All under `/api/`, JSON in and out; errors are one envelope everywhere: `{"error": {"code", "message", "detail"?}}` (404 `not_found`, 422 `validation_error`, 409 `cycle`). The actor recorded on activity/comments is the body's `actor`/`author`, else the `X-Actor` header, else (team mode) the name this browser picked, else the name of a member signed in with their own token (#474), else the first `team.people` entry in config.

| Method · path | What |
| --- | --- |
| `GET /api/version` | `{git_sha, built_at, asset_hash, schema_version}` — the build-identity contract the restart recipe checks |
| `GET /api/tasks?status=&parent=&project=&due=&due_from=&due_to=&type=&person=&owner=&q=&updated_since=&updated_before=&done_on=&include_closed=&descriptions=&limit=` (`person` and `owner` repeatable / comma-separated; `owner=<the install owner>` also returns every task nobody gave an owner, #476) | filtered flat list (summaries with `child_count`, `is_project`, `issue_ref`, `person`, `breadcrumb`, `root` = top ancestor, `last_comment`, `comment_count`, `blocked`, `blocker_count`, `blocked_by`). `status` repeatable/comma (`open` = not done/cancelled — the default) and takes the pseudo-values `deferred` ([Start dates & snooze](task-workflow.md#start-dates--snooze)) and `blocked` ([Blocked-by dependencies](task-workflow.md#blocked-by-dependencies)); `parent=root`; `project` = descendant-of; `due` = `today` · `week` · `overdue` · a date; `updated_since` = a date (modified on/after — the filter sheet's *modified* window); `updated_before` = a date (last touched strictly before — the *untouched > 30/60/90 days* stale windows compute it client-side, so the wire is a plain shareable date; any write counts as a touch, sync and mirror included, so a GitHub-synced task never looks stale); `done_on` = a date (the Board's *Done today* column); `done_from` / `done_to` = dates, an inclusive window over the closing day (the [done journal](views.md#views)'s page — with a window the list comes back **newest closing first**); `descriptions=false` leaves the `description` key off every item (the web app's boot asks for it — no list view reads one) |
| `POST /api/tasks` | create → 201 (`title` + any task field; `due` and `starts` accept the natural phrases below, `""` clears). No `status` given → **`todo`** — see [Inbox is for what arrives](inbox.md#inbox-is-for-what-arrives). Carrying an `external_id` (a capture source's own id, see [Capture into the Inbox](inbox.md#capture-into-the-inbox)) makes the create **idempotent**: first call 201, every replay **200** returning that same task untouched — and once that task is deleted, a replay is **410** `capture_dismissed` rather than a new task |
| `POST /api/tasks/bulk` `{ids, status?, due?, starts?, priority?, owner?, actor?}` | one change applied to many tasks (the Board/Today selection) → `{results: [{id, ok, task} \| {id, ok:false, error}], updated, failed}`. Every id is attempted and **200 is the partial-success code** — a bad id comes back as its own failure row rather than aborting or silently dropping the batch. `status: "complete"` rolls a recurring task's due (the row select's option, in bulk); `due` takes the natural phrases, resolved once for the request, `""`/`null` clears. Refused with 422: no `ids`, neither field, `complete` together with a `due`, or an unparseable phrase |
| `POST /api/tasks/bulk/delete` `{ids}` | delete many tasks, subtrees included (#121) → `{results: [{id, ok, deleted} \| {id, ok:false, error}], deleted, failed}` — the same per-id contract; `deleted` counts every row that went, a ticked child whose parent was deleted first reads `ok, deleted: 0` (it went with its parent) rather than a spurious not-found |
| `GET /api/tasks/tree?root=&include_closed=&descriptions=` | nested forest (`children`, `depth`); closed leaves pruned by default; `descriptions=false` leaves the `description` key off every node (the web app's boot asks for it — the closed tasks' text was most of a multi-megabyte payload and only the drawer reads it, from `GET /api/tasks/{id}`). The boot reads the **open** forest (no `include_closed`); the web app asks for the closed one only while a done / cancelled status is filtered (#309) |
| `GET /api/projects` | every task that has children, closed ones too — `{items: [{id, title, depth, status}]}` in tree order. The project filter reads it, because the boot's open forest holds a project whose children are all closed as a leaf (#309) |
| `GET /api/tasks/{id}` | detail: task + `breadcrumb`, `children`, `links`, `comments` (thread order), `activity` (newest first) |
| `PATCH /api/tasks/{id}` · `DELETE /api/tasks/{id}` | partial update (fields present only; `parent_id` goes through the cycle guard; `due` and `starts` natural or ISO, `""` clears) · delete the task **and its subtree** → `{id, deleted}` (the count that went; the detail's `descendant_count` says it beforehand — what the drawer's confirmation names, #121) |
| `POST /api/tasks/{id}/move` `{parent_id\|null}` · `POST /api/tasks/{id}/done` | re-parent · complete (recurring → roll) |
| `GET/POST /api/tasks/{id}/comments` `{body, origin?, author?}` · `PATCH …/comments/{cid}` `{body}` · `DELETE …/comments/{cid}` | thread · add → 201 · rewrite the body (author, time and `origin` unchanged; empty = 422) · remove |
| `GET/POST /api/tasks/{id}/links` `{url, label?, kind?}` (kind omitted → inferred from the URL by `tasks_repo.infer_link_kind`: `{…}` ref → folder, `mailto:` → email, an AI chat host → ai, a GitHub issue URL → issue, else web) · `PATCH …/links/{lid}` `{label}` · `DELETE …/links/{lid}` | links · rename a link's label (url/kind unchanged) · remove |
| `GET /api/tasks/{id}/blockers` · `POST …/blockers` `{blocker_id}` · `DELETE …/blockers/{blocker_id}` | the task's blockers · add one (201; 409 `cycle` on a self-block or a cycle) · remove one (404 if it wasn't a blocker) — see [Blocked-by dependencies](task-workflow.md#blocked-by-dependencies) |
| `PUT /api/tasks/{id}/issue` `{provider?, repo, number, url?, state?}` · `DELETE …/issue` | attach an existing issue (→ `coding`; the next sync fills state / url) · detach (→ `task`; the issue is untouched) |
| `GET /api/tasks/{id}/issue` · `POST /api/tasks/{id}/issue` `{repo}` | the drawer's panel: `{ref, info}` (the stored ref + the last-seen labels / updated time from the sync cache; `?live=1` asks the provider now) · **create an issue from the task** (title + description → `gh issue create`, assigned to you) and link it → 201 with the task (`409 already_linked` / `issues_disabled`, `502 provider_error`) |
| `GET /api/issues/status` · `POST /api/issues/sync` | `{provider, enabled, reason, sync_minutes, last_sync, last_result, last_error, last_error_code, next_run, repos}` · one sync pass now → the result counts (`409 issues_disabled` when not configured, `502 provider_error` with the classified `code` when `gh` fails) |
| `GET /api/activity?task=&limit=` | activity log, newest first (all tasks when no `task`) |
| `GET /api/dates?phrases=tomorrow,next week` | what each date phrase resolves to today → `{today, dates: {phrase: ISO \| null}}` — the same `src/dates.py` rule and clock the write path uses, so the date the sheet shows is the date a pick writes (#391); an unknown phrase is `422` |
| `POST /api/parse` `{text, today?}` | quick-add split → `{title, due, due_phrase, starts, starts_phrase, parent_ref, parent}` (`parent` resolved to `{id, title}` or `null`) |
| `GET/POST /api/people` · `GET/PATCH/DELETE /api/people/{id}` | people CRUD (`open_tasks` count included) |
| `GET /api/board?project=&person=&q=` | `{today, columns: {inbox, todo, standby, done}}` — the Board's buckets, same enriched summaries as the list; `done` = completed on the current local day only |
| `GET /api/today?person=` | `{today, due: [{root, items}], week: [{root, items}], counts: {overdue, today, week}, calendar}` — `due` = open tasks due ≤ today grouped by root project (sorted by due date within each group); `week` = tomorrow … +7 days in the same shape (the CLI's shape; the web app derives the due/week buckets from the filtered list itself and reads only `calendar` from here); `calendar` = the [calendar lane](task-workflow.md#calendar-beside-today): `{configured, reason, source, state, error, date, all_day: [{summary}], events: [{summary, start, end, starts_before, ends_after}], skipped_recurring, unreadable, fetched_at, failing_since, stale, refreshing}` — `state` is `ok` · `off` · `bad_url` · `unreachable` · `timeout` · `parse_error`, and `source` is the address's host, never the address |
| `POST /api/calendar/refresh` | fetch the calendar now (Settings' *Refresh now*) → the same `calendar` group `/api/today` carries, bounded by `calendar.timeout_seconds` |
| `GET /api/ai/suggestions` · `POST /api/ai/triage` `{task_ids?}` | list pending staged suggestions · ask the configured local model for exactly one suggestion per selected/current Inbox task. The entire response is validated before any suggestion is stored; malformed JSON, missing/extra task ids, invalid project/person ids, cycles, priorities or dates reject the whole run |
| `POST /api/ai/suggestions/{id}/accept` · `POST …/{id}/reject` | accept applies the staged parent, priority, due and person with activity actor `ai`, then moves the task to **Todo**; reject leaves the task untouched. Both resolve only that suggestion |
| `GET /api/search?q=&kinds=&limit=` · `GET /api/search/status` | **federated search** → `{q, took_ms, groups: [{kind, configured, reason, note, hits, count, took_ms, error, skipped}]}` — always the four groups `tasks · folders · emails · issues` in that order; an index that is not configured on this install is `configured:false` + `reason` (never silently absent), a failing one carries `error`; `kinds=tasks,emails` narrows which adapters run (the rest come back `skipped:true`); `limit` is per group. Every hit: `kind, title, subtitle, snippet` (`[match]` marks), `ref` (what attach stores: task id · folder ref · `.msg` ref · `owner/repo#N`), `url` (what open follows: `#task/id` · `taskos://open?ref=…` · the issue URL), `score` + kind-specific fields (`task_id, status, matched_in, breadcrumb` · `path, name` · `sender, date, folder, path` · `provider, repo, number, state, labels, task_id`) · the per-adapter configured / reason list for Settings |
| `GET /api/status` | `{https, auth: {enabled, password, client}, mirror: {enabled, dir, files, last_export, last_import, errors, error_files, watching, events, …}, backup: {enabled, dir, last_file, next_run, last_error, …}, folders: {enabled, roots, entries, last_indexed, indexing, stale, reason}, capture: {enabled, reason, source, poll_minutes, last_run, last_result, last_error, next_run, running}, voice: {enabled, reason, url, checked_at}, ai: {enabled, reason, model, checked_at}, archive: {configured, reason, running, repo, candidates, confidence_threshold, timeout_seconds, model, batch_size, examples, last_run, last_error}, opener: {install, uninstall, env_template, installed_here, mode}, placeholders}` — how this request came in (`client`: `loopback` · `token` · `public`) and what the install accepts; a disabled service carries its `reason`. `opener.mode` is `launcher` · `launcher-stale` · `fallback` · `null` — which registration shape this PC uses (see [Folders that open on any PC](folders.md#folders-that-open-on-any-pc)). `mirror.events` is the standing import-conflict/rejection count (issue #84) |
| `POST /api/mirror/export` · `POST /api/mirror/import` · `POST /api/backup` | run a full export / one watcher pass / one backup now (409 `mirror_disabled` / `backup_disabled` when not configured) |
| `POST /api/capture/email/run` | one flagged-email capture pass now → `{listed, created, unchanged, dismissed, errors, created_ids}` (409 `capture_disabled` + the reason when the poller is off) — see [Capture into the Inbox](inbox.md#capture-into-the-inbox) |
| `POST /api/archive/run` `{limit?}` (or `?limit=`) | start an archiving run → **202** with the run row in `running`; the work continues in a worker thread, because a full Inbox is walked over COM and takes minutes. `limit` bounds the run to at most that many mails, in the archiver's own plan order — what a first, undoable run uses. `409 archive_disabled` (with the reason) · `409 archive_in_flight` · and, once running, the run row itself carries `502` Outlook-unreachable / `504` timed-out as its `error` — see [Archive the Inbox](inbox-archive.md#archive-the-inbox) |
| `GET /api/archive/runs?limit=` · `GET /api/archive/runs/{id}` | every run, latest first → `{runs, count}` · one run **with its items** → the run fields (`planned, archived, needs_review, failed, error, agreement` — `agreement` is the share of model-ranked mails filed where the archiver's own suggester would have, `null` when the model ranked none) + `items: [{id, message_id, subject, sender, sent_at, attachments, candidates, chosen_folder, chosen_rank, confidence, reason, date_prefix, files, sequence, status, error, decided_at}]` — `chosen_rank` is the suggester's rank of the pick (0 = the model agreed), `confidence` and `reason` the model's own. Both read the database only, so a past run is still readable on a machine where the archiver is not installed |
| `POST /api/archive/items/{id}/revert` · `POST …/move` `{folder, hint?}` · `POST …/accept` `{hint?}` · `POST …/retry` | undo one mail (delete its files, move it back to the Inbox) · re-file it into another folder (a ref or an absolute path, resolved like `POST /api/resolve`) — an undo followed by a fresh filing · mark a `needs_review` / `failed` row seen, changing no file · finish a `failed` mail whose files are on disk by re-sending the same decision, unchanged (no body; a second refusal leaves the row `failed` with the archiver's newer message and answers `502 archive_retry_failed`). A move that lands, and an accept on a `needs_review` mail that had a folder, both write an `archive_corrections` row the next run's prompt carries; the optional `hint` (≤500 chars) is your one-line note on it. `409 archive_bad_state` when the row is in the wrong state, `404` when there is no such item, `422 archive_bad_folder` for a ref this install cannot resolve, `502` when the archiver refused |
| `POST /api/transcribe[?parse=0]` (body = the audio, `Content-Type` = its type) | the recorded quick-add line → `{text, parse}` — the transcript **and** the `POST /api/parse` split of it, in one round trip; `?parse=0` returns `{text}` alone, which is what the live-transcript pass asks for while you are still speaking. The body *is* the clip (no multipart), and what the browser sends is always 16 kHz mono WAV, which is the only thing either endpoint decodes. `409 voice_disabled` (no `voice.transcribe_url`) · `413 audio_too_large` · `422` (empty body) · `502 voice_rejected` (the endpoint answered and refused the clip, with what it said) · `503 voice_unavailable` (it never answered) — see [Voice quick-add](voice.md#voice-quick-add) |
| `POST /api/enrich` `{text, today?}` | the spoken line → `{title, description, due, due_phrase, starts, starts_phrase, parent, parent_ref, source, model, reason?}`. **Always 200** (except a malformed `today`, 422): the transcript is already on screen, so a hub that is down, slow or answering junk comes back as the deterministic [quick-add parse](#api) with `source: "parser"` and the reason — never an error the user reads as a broken microphone. `source` is `llm` or `parser` and is never omitted. See [Voice quick-add](voice.md#voice-quick-add) |
| `GET /api/mirror/events` · `DELETE /api/mirror/events` | inspect every standing import conflict/rejection (most recent first) · clear all of them → `{cleared}` |
| `POST /api/resolve` `{ref}` | a folder ref **or** an absolute path → `{ref, path, resolved, unresolved, href}`: `ref` folded onto the placeholders (`E:\onedrive\house` → `{onedrive}/house`), `path` this server's absolute path (display only), `href` the `taskos://open?ref=…` link. The value rides the body, not a `?ref=` query — that parameter name is on every tracking-parameter blocklist, so a URL-cleaning browser extension strips it off the URL before the request leaves the browser (#66). Task payloads carry `folder_resolved` + `folder_url` (a `links(kind=folder)` web URL, when one exists) so no client resolves a ref itself |
| `GET /api/folders/search?q=&limit=` · `POST /api/folders/reindex` | the folder index: substring AND over every indexed path → `{items: [{path, ref, name, depth}], count, indexing}` · rescan `search.folder_roots` now (409 `folders_disabled` when no root is configured / usable) |
| `POST /api/login` `{secret}` · `POST /api/logout` | a member's token or password → the 90-day `taskos_token` cookie, carrying **that member's own** token; in team mode the team password → the `taskos_team` cookie instead (`via: "team"`, `you`) · clear them |
| `GET /api/me` | who this request is (#474) → `{id, name, via, people: [{id, name}]}`: `via` is `token` (a member's own token — bearer or the cookie a token or password sign-in set), `team` (the name the team sign-in picked; `id` null when it is no member) or `loopback` (this PC with no credential = the install owner); `people` is the members list |
| `GET /api/time/meta` · `GET\|POST /api/time/timers` · `POST /api/time/timers/{person}/stop` `{minutes?}` · `DELETE /api/time/timers/{person}` | the time tracker (#457): people, areas + categories and the **server's** `today` / `now` · running timers · start `{person, category_id, switch?}` (409 `timer_running` unless `switch`, which stops and saves the running one in the same call) · stop and save (409 `no_timer` when it was already stopped — nothing is saved twice) · discard |
| `GET\|POST /api/time/entries` · `PATCH\|DELETE /api/time/entries/{id}` · `GET /api/time/entries.csv?period=\|from=&to=&area=&person=` · `GET /api/time/recent?person=` · `GET /api/time/summary?period=&area=&person=` · `GET\|PUT /api/time/guesses/{person}` · `POST\|PATCH /api/time/areas[/{id}]` · `POST\|PATCH /api/time/categories[/{id}]` | History (`q`, `limit`, `offset`) · time already spent `{person, category_id, day, minutes, start?, note?}` · edit any entry (404 when deleted meanwhile) · the counted entries as CSV · the last five categories · totals per person / area / category with coverage (`period` today · 7 · 30 · all) · a person's share guess, the others' only once theirs is in · area and category admin (409 `slug_taken`) |
| `GET /api/team` · `POST /api/team/name` `{name}` · `GET /api/team/avatars/{index}` | team mode: `{enabled, people: [{name, avatar}], you}` · pick this browser's name (the `taskos_name` cookie; 409 `team_disabled` when off, 422 for a name not in `team.people`) · that person's avatar image (404 without one) |

Also `GET /` shell · `GET /login` sign-in page · `GET /healthz` liveness · `GET /opener/opener.cmd` and `GET /opener/opener.ps1` (the per-PC opener's handler and launcher, public so a second PC's install one-liner can download them). Every `/api/` route except `/api/version` and `/api/login` needs the caller to be loopback or to carry the token — or, in team mode, the team cookie (see "Phone access & auth" and "Team mode").
