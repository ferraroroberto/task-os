# Voice quick-add

Hands busy? Open the add dialog, **click the mic beside line 1** and start talking. The button turns red and becomes a stop square, and the words appear on the line **as they are heard** — say *"buy a new filter for the dehumidifier next week"*, click again, and the line settles with the **Due** field already carrying next week's date, the same [quick-add parse](api.md#api) typing it would have produced, one confirming Enter from a task. Whatever was already on the line is kept: dictation adds to it rather than replacing it. Same gesture on the phone.

Nothing leaves the house: the clip's whole journey is **browser → task-os → [local-llm-hub](https://github.com/ferraroroberto/local-llm-hub)**. The phone reaches this app over its one Tailscale HTTPS endpoint and could not open the hub's port if it tried, which is why `POST /api/transcribe` forwards server-side rather than the page posting to the hub directly.

**Through the hub, not around it.** The request names **no model**, so the hub applies its own `roles.audio.transcribe` chain — **parakeet** on the Mac's ANE first, whisper behind it — and the call lands in the hub's observability ring. That is the fleet rule ("don't duplicate hub functionality in downstream apps") and it is what `voice-transcriber` already does. The local whisper server is the **fallback**, tried *only* when the hub could not be reached at all: an endpoint that answered and refused the clip has told you something, and quietly asking a different engine instead would turn one clear failure into two unclear ones.

**The browser converts before it uploads.** Neither end decodes a browser recording: whisper-server answers a bare `400 Invalid request`, the hub answers `400 audio conversion failed`. Probed live against each: **200** for a 16 kHz WAV, **400** for both formats a browser can record (webm/opus on Chrome, mp4/aac on iOS Safari). So `static/voice.js` taps the microphone through an AudioWorklet (`static/voice-worklet.js`), downmixes to mono, resamples to 16 kHz, lifts a quiet clip and writes a PCM WAV. The server side stays what it should be: a plain HTTP forward — no transcoding, no ffmpeg subprocess, no new dependency.

**The transcript arrives while you speak.** Every `voice.partial_interval_seconds` (default 1.5; `0` turns it off and transcribes once on stop) the page re-encodes the take *so far* and posts it to `POST /api/transcribe?parse=0`, replacing the provisional line. This is what `voice-transcriber`'s rolling worker does, minus its machinery: that app needs a session, chunk uploads and an SSE stream because its audio arrives as webm and has to be transcoded server-side by ffmpeg — this one already encodes WAV **in the browser**, so a partial is just an earlier prefix of the same buffer and needs no new route, no session and no streaming. It is affordable because parakeet answers a short clip in a fraction of a second. Partials carry **no parse**: a due date appearing and moving while the sentence is still landing is noise, so the dates and chips wait for the final pass, which is always the source of truth.

Capturing raw samples rather than a `MediaRecorder` blob is what makes that possible at all — a recording container cut off mid-take does not reliably decode (iOS Safari's fragmented mp4 certainly does not), while a complete WAV can be written from any prefix of the sample buffer. It also takes one decoding step *out* of the pipeline.

**The spoken sentence becomes a title and a description.** A sentence you say carries more than a title — *"urgent, I need to call the plumber about the leaking radiator in the guest room before friday"* is a title, a description and a date. Once the transcript has settled, the page asks `POST /api/enrich`, which sends it to the hub's light model (`enrich.model`, default `agentic_light_nothink`) and comes back with a short imperative title and the rest as a **Description** — both landing in the fields where you can still change them. Typing is untouched: a typed line keeps its instant deterministic parse, so `POST /api/parse` and the CLI still agree on what a phrase means.

**The model may point at a date; it may not pick one.** Asked live for *"before friday"* with today Monday 2026-09-07, it answered `2026-09-13` — a **Sunday**; Friday was the 11th. So it is asked for the *phrase*, and two guards stand behind that: the phrase must appear **verbatim** in the transcript or it is dropped, and `src/dates.py` — not the model — turns it into a day. A model that returns a resolved ISO date instead has that date discarded. The cost is a date occasionally missed; the cost of the alternative is a task confidently due on the wrong day.

**Schema-constrained decoding is not available here**, so the JSON is asked for in the prompt and validated in `src/enrich.py`: an OpenAI `response_format: json_schema` request to this model comes back `400 Failed to initialize samplers: Unexpected empty grammar stack after accepting piece: <think>` — its template injects a thinking prefix the grammar cannot accommodate, and `agentic_light_nothink` (the same llama-server) fails identically. The reply is stripped of any `<think>` block and any code fence, parsed, and read through an allow-list of the four keys the form has.

**Losing the tidy-up is not losing anything.** Every failure — no `enrich.url`, the hub down, a timeout, a refusal, junk instead of JSON — leaves the transcript and its deterministic parse exactly where they were, reported as `source: "parser"` with the reason. Nothing is blocked on it: it takes about 1.5 s warm, and the line is already usable before it starts.

**Off is a visible state, never a dead button.** No `voice.transcribe_url`, no endpoint answering (the probe is one cached TCP connect per endpoint — port 8090 is shared with the fleet's other transcriber, so a connect that never comes back does not say *which* of "down" and "busy" it was, and the reason names both rather than picking one; nothing is ever retried in a loop), a browser with no AudioWorklet, a page that is not a secure context, a refused microphone: each leaves the mic visible and disabled with its own sentence under the field. The same sentence appears in Settings → *Voice quick-add*, in `GET /api/status` under `voice`, and in `tasks mirror status`'s `voice` line — as does **which** endpoint is serving (`hub` or `local whisper (fallback)`), so "am I getting parakeet, or the CPU fallback?" is answerable without reading a log. Each transcription also logs what actually served it, from the hub's own `x-hub-served-model` header.

Out of scope for now: dictating descriptions and comments directly, enriching *typed* lines, voice through the global hotkey window, translation.
